## P0 — App shell and Harbor integration

- [x] **Scaffold and run.** Use Vite, React and React Router. Configure dev and preview to use strict port `5512`. Keep the lockfile and make `npm run build` produce a self-contained `dist/`. Use the text brand “my Social Security” in the masthead and browser title. Use local assets and system fonts.
- [x] **Shell and routes.** Implement Overview `/`, Benefit statements `/statements`, statement detail `/statements/:statementId`, Direct deposit `/direct-deposit`, Letters `/letters`, and letter detail `/letters/:letterId`. Use the masthead, layout and accessible responsive navigation in DESIGN.md. Overview links directly to every workflow. Populate it with the signed-in name, current benefit and masked payment destination, links to recent documents, and derived unread notice count. Each route, including unknown IDs, handles direct entry and reload inside the same providers. Unknown IDs show a return link to the relevant index. All navigation preserves `?sid=` and non-router internal links use `withSid()`.
- [x] **Harbor state.** Import `stateApi(createInitialData)` from `../../templates/state-api.js` in Vite config and copy `templates/dataManager.js` unchanged to `src/utils/dataManager.js`. Use `my_social_security` consistently as the store key. Await one `loadState(APP, createInitialData)` behind a neutral loading screen before mounting routes. Keep one store mutation path that passes the complete next state to `saveState` once per committed action. Keep passive route rendering, filtering, form drafts, and idle tabs free of business writes. Use the template’s actual JSON `GET /go` rather than a competing page route, and preserve its `initial_state`, `current_state` and `state_diff` shape.
- [x] **Injected data and verifier docs.** Put deterministic defaults in `src/data/seed.js`. Handle replaced arrays of zero, one or hundreds of records, incomplete records, and unavailable relationships without repopulating arrays or manufacturing data. Read the runtime clock with `new Date()` for current dates. Document the implemented top-level keys, shapes and exact writes in `SCHEMA.md`. The [data model](assets/data_model.md) is the implementation target.

## P1 — SEED workflows

- [x] **Benefit statements.** The statements index has separate “Social Security Statements” and “Tax benefit statements” views. Search by title, year or form, filter by year, and sort newest/oldest within the selected view. Open a statement to show its dated snapshot, earnings and recorded estimate figures where available. Tax statements show the tax year, form type, benefits paid, repayments and net benefits. Detail supports “Download PDF” and “Print”. An explicit open from a statement list or Overview appends one `statementActivity[]` event with `action: "viewed"`. Explicit Download and Print append one event with `downloaded` or `print_requested`, respectively. Every event carries its own `id`, `statementId`, `kind`, `year`, `status`, `actorId` and `createdAt`. Deep links, reloads and searching alone do not append events.
- [x] **Direct deposit.** Show the current institution, account type and masked account ending, a change history, and a “Set up direct deposit” or “Change direct deposit” action as applicable. The form collects a synthetic bank label, checking/savings, a 9-digit routing number, and an account number plus confirmation. Require digits, a matching confirmation, and a 4–17 digit account number. Review shows only masked numbers, with Back to edit, Cancel and Confirm. On confirm, update `directDeposit` and append a `directDepositChanges[]` record in the same write, with previous and new masked destination, `changeType`, `status: "confirmed"`, `actorId`, `createdAt`, and its own `id`. Return a receipt with reference ID. Reopening the route shows the confirmed destination. Form inputs, failed validation, Back and Cancel do not write. Never persist full routing/account numbers or confirmation input. If the profile is ineligible, explain unavailability and omit the form.
- [x] **Benefit Verification Letter.** Show a “Get benefit verification letter” action on Letters and Overview. Present a review of the current subject and benefit status. Upon “Generate letter”, create a single ready `letters[]` record containing the subject, benefit snapshot, `type: "benefit_verification"`, `status: "ready"`, `actorId`, `createdAt` and its own `id`. Open the generated letter with working Download and Print controls. Populate the letter from the beneficiary’s own status (receiving, not receiving, or pending). Saving or printing a letter appends a separate `letterActivity[]` event with the letter ID and `action: "downloaded"` or `"print_requested"`; inspecting drafts or leaving the review makes no writes.
- [x] **Letters and notices archive.** List verification letters and account notices together, with type and unread filters, search by title, and date sorting. Notice detail presents the dated account correspondence. Explicitly opening an unread notice from the index or Overview, or using “Mark as read” on its detail page, updates `letters[].readAt` and appends `letterActivity[]` with `action: "marked_read"` and the related `letterId` in the same write. Later opens of the same notice do not repeat that write. All letters can be reopened from the archive and use the same Download and Print actions. The unread count is derived.
- [x] **Local workflow verification.** Use Chromium via the Node Playwright installation at `PILOT_PLAYWRIGHT`. Start any persistent Vite process using PowerShell `Start-Process -WindowStyle Hidden` with the absolute Vite entry point and the app directory as its working directory. On localhost port `5512`, test statement and tax form selection, PDF delivery and print invocation, direct deposit setup and change (including validation and cancel), letter generation/access, and unread notice changes. Read `/go?sid=…` after each action and verify exact affected fields, stable IDs and unrelated state. Exercise reloads, deep links, different sessions, injected empty/single/large collections and optional fields, mobile layout, and no idle writes. Capture the actions and observable fields in `TEST.md`. Keep test scratch in an ignored directory or remove it. The parent runner handles Docker certification and commits.

## Seed requirements

- [x] Use a fictional, pre-signed-in retirement beneficiary, Maren Ellis, with an active checking destination at a fictional bank. Include 24 Social Security Statement snapshots, six recent tax years with an SSA-1099, at least 30 earnings rows, 24 monthly payments, 24 historical deposit changes, and at least 24 letters/notices. Use fixed IDs, natural English, useful date ranges, numeric amounts and mixed read status. Keep existing access-event arrays empty so new actions are easy to inspect. See [data fixtures](assets/data_model.md#initial-state).
- [x] Build original local icons and artwork to the [design specification](DESIGN.md). Generate PDF content locally from the selected synthetic record and use the same content for print. Mark output documents “Sample · Synthetic data”. Keep downloads, in-app links and runtime assets local.

## Scope

The account starts signed in. Authentication, identity verification, live agency or bank access, sending mail, applications, contact changes and representative payee workflows are outside this phase.
