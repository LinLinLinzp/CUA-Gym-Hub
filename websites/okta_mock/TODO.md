## P1 — Primary workflows

- [x] **P1.1 — Users.** People lists name and username, primary email, department and status. Search across names, usernames and emails, filter by status, and page through results. **Add Person** collects first and last name, username, primary email, optional secondary email, department and title, and an Active or Staged initial status. Trim fields, validate email-form identifiers, and reject an existing username case-insensitively. Provide Profile, Groups and Applications views on the person page. **Edit Profile** pre-fills editable fields. Expose context-valid Activate, Suspend, Unsuspend and Deactivate actions with confirmation, and Delete only after deactivation. Create appends `users[]` with ID, profile, `status`, `createdAt`, `createdBy`, `updatedAt` and `updatedBy`. Edit updates profile fields and update metadata. Lifecycle changes update `status` and update metadata. Delete removes the user, their memberships and their direct assignments. Every action appends `activityEvents[]` with actor, timestamp, action, target and relevant status changes or removed IDs. Groups and Applications use the shared actions from P1.2 and P1.3.
- [x] **P1.2 — Groups and group membership.** List group name, description, source and member count. Provide search, source filter and paging. **Add Group** collects a unique case-insensitive name and optional description. The detail view exposes Members and Applications, and **Edit Group** saves changes to name and description. **Assign People** opens a searchable multi-select of eligible nonmembers, saves the chosen members together, and updates both the group and person views. Confirm membership removal and group deletion. Create adds `groups[]` with ID, profile, source and creation/update metadata. Edit updates `name`, `description`, `updatedAt`, `updatedBy`. Membership adds `groupMemberships[]` records carrying `groupId`, `userId`, `status`, `createdAt`, `createdBy`; removal removes the matching records. Deleting a group removes its memberships and assignments to that group in the same update. Append `activityEvents[]` for each affected relationship or group operation, recording related IDs and cascade IDs on group deletion.
- [x] **P1.3 — Application assignments.** List app name, category, status and assignment counts with search, status filter and paging. Make Assignments the default app detail view. Present People and Groups tabs with an **Assign** control offering **Assign to People** and **Assign to Groups**. Show searchable eligible targets, allow selection and confirmation, and exclude duplicate direct assignments while allowing a direct grant alongside inherited access. Show Direct and Via group sources on effective access rows, keeping multiple group sources visible. Unassign a direct grant or a group grant with confirmation. Use the same write path if initiated from a person's or group's Applications view. Assign adds `appAssignments[]` containing `id`, `appId`, `principalType`, `principalId`, `status`, optional `appUsername` for direct assignments, `createdAt` and `createdBy`. Unassign removes the exact grant. Both append `activityEvents[]` with `appId`, principal identity and assignment ID. Derive inherited access from membership and group grants, including when one path is removed and another remains.
- [x] **P1.4 — Workflow evidence.** At `http://localhost:5410` use Node Playwright from `PILOT_PLAYWRIGHT` and installed Chromium. Use fresh `sid` values and put scratch files in a gitignored site directory or remove them. In `TEST.md` record browser steps and actual changed fields from `/go` for user creation/edit/lifecycle, group creation/edit/member add/remove, and app person/group assign and unassign. Include a reload check, a case with both direct and inherited access, and a check that removing one grant leaves the other effective. Check an injected empty/sparse state, session isolation, deep links, and zero idle POSTs after boot. The parent runner handles Docker certification and commits after `TEST.md` is produced.

## Out of scope
