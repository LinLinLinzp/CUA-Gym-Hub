## P0 | Shell and Harbor runtime

- [x] **P0.1 Account shell and offline build.** Build a React/Vite SPA in this directory. Set the title to `Sephora | My Account` and use `SEPHORA` as a plain text wordmark. Render Overview, Orders, Beauty Insider, and Returns in a responsive navigation bar and keep the active destination visible. Build the overview from recent account activity, useful shortcuts, and the current points balance. Use the original design and local art direction in `DESIGN.md`. Keep dependencies in the lockfile and pass `npm run build`. Use port 5343 with strict port handling for development and preview.
- [x] **P0.2 Routes and sessions.** Provide `/`, `/account/orders`, `/account/orders/:orderId`, `/account/beauty-insider`, `/account/returns`, `/account/returns/new/:orderId`, and `/account/returns/:returnId`. Keep all routes within their required providers. Support hard reloads, browser history, useful missing-record states with links back, and `?sid=` on every internal navigation. Use `withSid()` for links that leave the SPA router.
- [x] **P0.3 State bootstrap and API.** Copy `templates/dataManager.js` unchanged to `src/utils/dataManager.js`, import `stateApi(createInitialData)` from `../../templates/state-api.js` in the Vite config, and export defaults from `src/data/seed.js`. Await `loadState('sephora', createInitialData)` behind a neutral loading state. Centralize mutations and call `saveState` once per successful user action with the full next state. The shared API owns `/go`, `/state`, and `/post`. Confirm the initial baseline, session isolation, reload persistence, and zero writes after bootstrap while idle. Handle missing optional fields, replaced arrays, unknown IDs, and lists of hundreds without overwriting injected data.
- [x] **P0.4 Observable schema.** Write `SCHEMA.md` from the implemented shapes, including every top-level key and an **Observable State Changes** table. List the exact keys updated, IDs linking records, and amount, quantity, actor, status, and timestamp fields for every committed workflow. The planned schema and test assertions are in `assets/data_model.md`.

## P1 | Required account workflows

- [x] **P1.1 Orders and tracking.** Search by order number or line-item name, filter by status and date window, sort by date, and show results with count and clear-filter controls. Open an order to see items, quantities, totals, payment summary, fulfillment, and relevant status dates. Reveal shipment tracking inline or in a dialog, including the carrier, tracking number, and dated events. Show separate shipments when present. History, filtering, details, and tracking are read operations with zero persisted writes.
- [x] **P1.2 Orders | Cancel an eligible order.** Offer `Cancel order` on a confirmed eligible, unshipped order in `placed` or `in_progress` status before its explicit `cancelUntil`. Show the order number and authorized total in the confirmation. On confirmation, update `orders[].status` to `cancelled`, set `orders[].cancelledAt`, and append one `orderEvents[]` record with `orderId`, `type`, `status`, numeric amount, currency, affected line IDs and quantities, actor, and `createdAt`. Use unfulfilled, uncredited orders for this action. Recheck eligibility on confirm and keep the action single-use. Closing the dialog leaves `/go` unchanged.
- [x] **P1.3 Beauty Insider | Balance, activity, and redemption.** Display the member tier, current points balance, and a dated signed-point ledger with activity filters. Link earn and return entries to the relevant order or return when available. Show a small rewards catalog with visible points costs and stock or eligibility feedback. Provide a confirmation for an available reward that can be redeemed with points alone. On confirm, decrement `beautyInsider.pointsBalance` and `rewards[].stock` and append one linked `redemptions[]` record and one negative `pointsTransactions[]` record in a single update. The confirmation names the reward, cost, and remaining balance. Sold-out, insufficient-points, duplicate submissions, and dialog dismissal leave state unchanged.
- [x] **P1.4 Returns | Start and submit a mail return.** Open from a delivered order or from Returns via an eligible-order picker. In one form, select eligible lines and quantities, require a reason per selected line, and review the estimated item refund and original payment summary. Validate remaining quantity against existing active or completed returns at review and at submission. On submit, append exactly one `returns[]` record with `status: 'submitted'`, `orderId`, selected line IDs, quantities, reason codes, estimated line refunds and total, currency, refund method, actor, and `createdAt`. Show confirmation and a link to that return. Keep actual refunds and point adjustments out of submission. The submitted return immediately affects remaining returnable quantities through its linked lines.
- [x] **P1.5 Returns | Find and track requests.** Search by return or order number and filter by status. Open return details to see requested items, quantities, refund estimate or completed amount, timeline, and the linked original order. Supply local mail-back instructions for a submitted request and show completed refund information when present in the fixture. Browsing and tracking are read operations with zero persisted writes.

## Data seed | Required in P0/P1

- [x] **Orders.** Seed 36 orders with fixed IDs and realistic English product names, mixed totals and 1–5 lines each. Include a fresh cancellation candidate, a split shipment, delivered eligible orders, an older delivered order, and a partially returned multi-quantity line.
- [x] **Beauty Insider.** Seed one synthetic VIB member, 40 reconciled point entries, 8 reward offers, and 8 historical redemptions. Include affordable, unaffordable, sold-out, and purchase-required offers.
- [x] **Returns.** Seed 24 returns across enough distinct orders to support list filtering. Include submitted, in-transit, completed, and cancelled examples, multiple reasons, and both single- and multi-line requests. Link every seeded return and point reversal to real records within the fixture. Use default dates from the fixture calendar in `assets/data_model.md`.
